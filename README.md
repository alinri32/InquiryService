# مستندات پیاده‌سازی سرویس وب استعلام (Inquiry Service API)

---

### ۱. روش اجرای پروژه

#### پیش‌نیازها
* دات‌نت نسخه **.NET 10.0**
* پایگاه‌داده **Microsoft SQL Server** (نسخه ۲۰۱۹ به بالا )

#### مراحل راه‌اندازی و اجرا
1. **پایگاه‌داده و اجرای اسکریپت‌ها:**
   * ابتدا اسکریپت ساخت دیتابیس و جداول موجود در مسیر `sql/InquiryDb.sql` را در SQL Server اجرا کنید.
   * این اسکریپت دیتابیس `InquiryDb`، کاربر و دسترسی‌های `Ayan` و جداول `Inquiries` و `InquiryProviderAttempts` را به همراه فشرده‌سازی صفحه‌ای (`PAGE Compression`) ایجاد می‌کند.

2. **تنظیم Connection String:**
   * در فایل `src/InquiryService.Api/appsettings.json`، مقدار کانکشن‌استرینگ `InquiryDb` را متناسب با محیط خود بررسی و تنظیم کنید:
     ```json
     "ConnectionStrings": {
       "DefaultConnection": "Server=localhost;Database=InquiryDb;User Id=Ayan;Password=StrongP@ssw0rd!;TrustServerCertificate=True;"
     }
     ```

3. **اجرای تست‌های واحد (Unit Tests):**
   * برای اطمینان از صحت عملکرد منطق Failover، بیزینس ارور، Idempotency و کش:
     ```bash
     dotnet test
     ```

4. **اجرای سرویس:**
   * دستور زیر را در خط فرمان اجرا کرده و به آدرس Swagger سرویس مراجعه کنید:
     ```bash
     dotnet run --project src/InquiryService.Api
     ```
   * آدرس پیش‌فرض مستندات: `https://localhost:<port>/swagger`

### توضیح مختصر معماری

این پروژه بر اساس اصول **معماری کلین (Clean Architecture)** و به صورت عمل‌گرایانه (Pragmatic) طراحی و پیاده‌سازی شده است تا وابستگی‌ها معکوس و جریان اطلاعات به سمت هسته سیستم باشد:

* **لایه دامنه (InquiryService.Domain):**
  * هسته مرکزی سیستم بوده و شامل موجودیت‌های اصلی (`Inquiry` و `InquiryProviderAttempts`)، شمارنده‌ها یا اینام‌ها (`InquiryStatus`, `ProviderErrorType`) و مدل‌های پایه‌ای خروجی مانند `Result<T>` است.
  * این لایه کاملاً خالص و فاقد هرگونه وابستگی به فریم‌ورک‌های بیرونی، ابزارهای وب یا کتابخانه‌های دسترسی به پایگاه داده است.

* **لایه کاربرد (InquiryService.Application):**
  * این لایه مسئول هماهنگی و ارکستراسیون منطق تجاری است.
  * شامل اینترفیس‌های ارائه‌دهنده سرویس (`IInquiryProvider`)، قراردادهای کشینگ (`IInquiryCacheService`)، مخزن داده (`IInquiryRepository`)، اشیاء انتقال داده (DTOs) و کلاس اصلی رهبری فرایندها (`InquiryOrchestrator`) می‌باشد.

* **لایه زیرساخت (InquiryService.Infrastructure):**
  * پیاده‌سازی دسترسی به پایگاه داده SQL Server را با استفاده از ابزار سریع و سبک **Dapper** و کوئری‌های خام و بهینه‌سازی‌شده SQL بر عهده دارد.
  * پیاده‌سازی سرویس کش موقت (`MemoryInquiryCacheService`) و شبیه‌سازهای سرویس‌دهندگان (`PrimaryMockProvider`, `SecondaryMockProvider`) در این لایه قرار گرفته‌اند.

* **لایه واسط کاربری/ارائه (InquiryService.Api):**
  * نقطه ورودی برنامه و شامل کنترلرهای RESTful، نگاشت ورودی‌ها و اعتبارسنجی اولیه، مدیریت مرکزی خطاها از طریق Middleware اختصاصی و پیکربندی تزریق وابستگی‌ها (DI) است.

### تصمیمات مهم فنی (Architectural & Technical Decisions)

* **دریافت کلید تکرارناپذیری از طریق هدر استاندارد HTTP (`Idempotency-Key`):**
  * به منظور پایبندی به استانداردهای بین‌المللی API و تفکیک متادیتای پروتکل انتقال از داده‌های تجاری، فیلد تکرارناپذیری به عنوان هدر HTTP در نظر گرفته شده است.
  * یکتایی در لایه پایگاه داده توسط شاخص اختصاصی (`UX_Inquiries_IdempotencyKey`) تضمین می‌شود تا از ارسال و پردازش درخواست‌های تکراری و ایجاد تراکنش‌های موازی جلوگیری به عمل آید.

* **تفکیک خطاهای فنی و بیزینسی در چرخه Failover:**
  * در صورت مواجهه با خطای فنی (Technical Error) یا تایم‌اوت (Timeout) در سرویس‌دهنده دارای اولویت، ارکستراتور به صورت خودکار به سراغ سرویس‌دهنده بعدی در زنجیره اولویت می‌رود.
  * در صورت بروز خطای بیزینسی (Business Error مانند عدم تطابق هویت)، زنجیره سوئیچینگ بلافاصله متوقف می‌شود؛ چرا که مراجعه به ارائه‌دهندگان دیگر ماهیت نامعتبر بودن داده را تغییر نمی‌دهد و تنها هزینه اضافی ایجاد می‌کند.

* **الگوی کش داده‌ها (Cache-Aside Pattern) به همراه قابلیت دور زدن (Bypass):**
  * نتایج استعلام‌های موفق جهت افزایش سرعت پاسخ‌دهی و کاهش ترافیک سرویس‌دهنده‌ها کش می‌شوند.
  * کلاینت می‌تواند از طریق ارسال پارامتر `bypassCache: true`، کش را دور زده و استعلام مستقیم دریافت نماید.

* **استفاده از الگوی Result به جای پرتاب استثنا (Exceptions):**
  * مدیریت وضعیت و خطاهای سرویس‌دهنده‌ها با بازگرداندن اشیاء ساختاریافته `ProviderExecutionResult` پیاده‌سازی شده است تا از ایجاد سربار عملکردی ناشی از Stack Trace در استثناهای پیش‌بینی‌پذیر شبکه جلوگیری شود.

* **بهینه‌سازی پایگاه داده با Dapper و فشرده‌سازی صفحات (PAGE Compression):**
  * جهت دستیابی به بالاترین کارایی I/O و حداقل تأخیر (Low Latency)، به جای ORMهای سنگین، از میکرو-ORM دپر با رویکرد Database-First استفاده شده است.
  * در اسکریپت پایگاه داده، جداول اصلی و ایندکس‌ها با قابلیت `PAGE Compression` پیکربندی شده‌اند تا مصرف حافظه و دیسک کاهش یابد.

### فرضیات در انجام تسک (Assumptions)

* **قراردادهای داده‌های آزمایشی برای شبیه‌سازی وضعیت‌ها:**
  * فرض شده است که برای تست رفتارهای مختلف سیستم، پیشوندهای خاصی در شناسه ورودی به کار گرفته می‌شوند: شناسه‌های شروع‌شده با `999` شبیه‌ساز تایم‌اوت، شناسه‌های با `888` شبیه‌ساز خطای فنی و شناسه‌های با `777` شبیه‌ساز خطای تجاری (Business Error) هستند. سایر شناسه‌ها (معتبر بر اساس کد ملی ایران) موفقیت‌آمیز فرض می‌شوند.
* **طول و نوع فیلدهای ورودی:**
  * طول شناسه استعلام حداکثر ۱۰ کاراکتر عددی (مطابق با ساختار کدهای ملی در سناریوی فرضی) در نظر گرفته شده است و سایر پارامترها دارای محدودیت‌های طولی تعیین‌شده در لایه DTO هستند.
* **طول عمر پیش‌فرض حافظه موقت (Cache TTL):**
  * مدت زمان اعتبار کش پاسخ‌های موفق در صورت عدم تعیین در تنظیمات بیرونی، به صورت پیش‌فرض برابر با ۱۰ دقیقه فرض شده است.
* **هم‌پوشانی و فرمت داده‌های سرویس‌دهندگان:**
  * فرض شده است که سرویس‌دهندگان مختلف توانایی ارائه خروجی مشابه برای نوع استعلام درخواستی را دارند و نتیجه به شکل متن/JSON خام دریافت و در لایه لاگ و دیتابیس ثبت می‌گردد.
